# Updating and backups

## Moving an existing docker compose install to Flisk

Do this once, before `git pull` deletes `docker-compose.yml`. Your data lives in Docker volumes, so none of it is lost, but the
Flisk services use differently named volumes and need the old containers out of the way.

```sh
cd tubehaus                      # the checkout you ran `docker compose up -d` in
docker compose down              # stops the old stack and frees ports 80 and 443. Never add -v: that deletes the volumes
git pull
```

**If you ran TubeHaus behind your own proxy** (`TUBEHAUS_HTTP_BIND=127.0.0.1:8080` or similar in `.env`): those variables no
longer exist. Before the first `flisk up`, edit `services/tubehaus/caddy/service.json` so Caddy stays reachable only from this
machine: set `"extraPorts": [{ "port": 80, "hostPort": 9080 }, { "port": 443, "hostPort": 9443 }]` (no `"bind"`), and point your
proxy at `http://127.0.0.1:9080`. Left as it is, Caddy is published on every network interface (`"bind": "0.0.0.0"`), so anyone
who can reach the server could skip your proxy and its login.

Copy each volume to its new name. The old names start with your Compose project name (the folder name, `tubehaus` if you cloned
it that way; `docker volume ls` shows them) and the new ones with `tubehaus-tubehaus-autogenerated_`. Replace `tubehaus_` below if
yours differs:

```sh
for v in tubehaus-data warp-data postgres-data caddy-data companion-cache; do
  docker volume create tubehaus-tubehaus-autogenerated_$v
  docker run --rm -v tubehaus_$v:/from:ro -v tubehaus-tubehaus-autogenerated_$v:/to alpine cp -a /from/. /to/
done
flisk up
```

The old volumes stay as they are, so you can go back by checking out the previous commit and running `docker compose up -d`.
Remove them with `docker volume rm tubehaus_<name>` once the new setup works.

## Update

```sh
cd tubehaus
git pull
flisk down
for image in ghcr.io/biolend83/tubehaus:latest quay.io/invidious/invidious:latest quay.io/invidious/invidious-companion:latest \
             brainicism/bgutil-ytdlp-pot-provider caddy:2 postgres:14; do
  docker pull "$image"
done
flisk up                        # recreates the containers from the newer images
```

Your library, the WARP registration and the Invidious database live in Docker volumes, so they survive updates.

YouTube changes things often, and most breakage is fixed upstream in invidious-companion. If videos suddenly stop
playing, pulling the newest images and running `flisk down && flisk up` is the first thing to try. Watch this repository's releases
(Watch → Custom → Releases) to hear about TubeHaus updates.

## What to back up

Flisk prefixes each Docker volume with `tubehaus-tubehaus-autogenerated_` (`docker volume ls` shows them).

| Volume | Contents | Needed? |
|---|---|---|
| `tubehaus-data` | your library: subscriptions, history, resume points, playlists (`ytlib.json`), subtitle cache | **yes** |
| `postgres-data` | Invidious' database (mostly cache) | optional |
| `warp-data` | the WARP registration; a new one is created if it's missing | no |
| `caddy-data` | HTTPS certificates; Caddy gets new ones if it's missing | no |

The easiest backup is in the app: **Settings → My data → Export → TubeHaus backup**. It's one JSON file with
everything (subscriptions, history, resume points, playlists, likes, Shorts preferences), and **Import from file**
restores it on any TubeHaus.

From the command line instead:

```sh
docker cp tubehaus-tubehaus-autogenerated-tubehaus-1:/data/ytlib.json ./ytlib-backup.json
```

Restore it:

```sh
docker cp ./ytlib-backup.json tubehaus-tubehaus-autogenerated-tubehaus-1:/data/ytlib.json
flisk restart tubehaus
```

## Moving to another server

1. Back up `ytlib.json` as above
2. Install TubeHaus on the new server with the same `.env`
3. Restore `ytlib.json`, then point your DNS at the new server
